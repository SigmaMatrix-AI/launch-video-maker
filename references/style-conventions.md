# Style 包约定

Style 是可与不同参考模板交叉组合的表面视觉表达，负责颜色、字体及兼容的材质、光影等。它不是模板变体列表，也不是统一主题插件接口。

以实际 `styles/` 目录为准发现正式包；开发 fixture 和旧样例不自动成为正式候选。

## 发现和阅读

后续每个 style 使用 `styles/<style-id>/` 文件夹，并包含入口 `style.md`。发现候选时读取其文档；选中后继续读取其中与本片有关的附属说明、参考实现和素材。

`style.md` 由作者自由描述字体、排版、布局、动效、材质、光影、视觉 tone 或其他重要特征。**不要求 frontmatter、固定字段、统一章节、固定 token 表或 schema。** Agent 应理解文档，不依赖字段解析器判断 style 是否有效。

没有 `style.md` 的目录不视为完整 style 包；可以报告缺失并选择其他方向，不自行编造该目录的风格定义。

## 附属资源引用

文档可链接包内的参考实现、图片、字体、纹理及其他素材。相对路径均相对于引用它的文档；代码资源引用则按其实际模块或构建约定解析。确保链接可解析，必要时说明运行方法、来源与使用条件。

外部参考链接可以帮助理解风格，但不能成为影片运行时隐式加载的必需资源。采用的实现与允许使用的素材应保存到当前影片工程；保留来源及参考版本，不能依赖某个作者机器的绝对路径。

## 与品牌、模板组合

明确的用户要求和品牌规范优先。参考影片/模板决定动作、镜头、空间调度、布局、转场与节奏；style 只在保留这些结构的前提下应用颜色、字体及兼容的表面处理。style.md 可以自由描述布局与动效，但这些描述不覆盖选定参考的运动与构图。记录实际采用的表面特征和未采用内容，不能声称完整还原了未应用的 style 特征。

主题色只是 style 的输入之一，默认作少量点缀；背景、正文和辅助色按 style 组织，避免全片同色化。Logo 与真实产品截图、官方案例保持原色，不能套品牌色滤镜。没有明确品牌字体要求时采用 style 的字体，不主动搜集整套品牌字体。

“品牌色作点缀”不等于“其他颜色全部去掉”。先识别参考中的舞台底色、控件表面、语义强调、功能状态、作品内容和动作/转场色：多色渐变、彩色内容墙、局部满屏高饱和段落可以各有用途。style 可调整相应色谱，但应保留颜色承担的层次、识别和节奏作用；不将所有颜色归并成一个主题色，也不把真实作品改绘成同一配色。

先固定参考的对象位置、尺寸关系、运动路径与时间点，再替换视觉属性。换字体造成溢出时优先调整文案、字号和局部间距，保持参考构图；不要因此退回通用的“标题加面板”结构。没有可用参考时，根据产品和用户要求自主设计镜头，仍明确区分镜头设计和 style 的表面作用。

不要求模板实现通用的 `styleId` 切换器，不要求每个 style 都有代码，也不要求每个模板提前支持所有 style。组合效果通过最终场景的实际视觉和动态表现验收。

## 目录为空时

记录“暂无内置 style”，根据产品证据、[brand kit](brand-kit.md) 和用户要求制定本片视觉方向。后续 [审查](review.md) 的“风格还原”以该已记录方向及用户参考为基准，不能因没有内置 style 就免评或自动给高分。

## 应用示例与开发输入

普通 style 只需自由格式 style.md，不强制 style.json 或固定字段。复杂 style 的 demo 是风格应用示例，不是模板，无须独立运行。不因缺少原工程依赖就判定 style 不完整；只参考适用局部，不修复或移植原 demo 引擎，也不复制其叙事、品牌和角色。用户初始样例的 STYLE.md 可按明确入口读取，正式入库时再统一命名。
